# 从用户意图验证最终效果与数据责任

## R · 原书依据

第 12 章，PDF 物理页 459–466、482–496、497–506。客户端、队列和接收方可能各自重试。用户意图的标识要跨过这些边界，派生结果还须接受独立核查。自动决策会影响具体的人，评审也应明确数据用途、纠错途径与责任人。

## I · 如何选择

先写可直接核对的不变量，例如“同一有效退款请求至多产生一笔支出”。区分完整性和新鲜度：视图延迟可设置期限，重复付款必须识别并修复。不可逆效果之前执行必要约束；允许事后补偿的业务要说明谁承担补偿成本、怎样发现违约。对个人作出的不利决定另列申诉与更正链。

## A1 · 从原书到演练

原书用转账成功但客户端收不到回复说明重试能再次执行业务动作（PDF 483–485）。合成演练：退款 80 元，支付方已受理，网关超时。客户端再次提交同一请求 R7。保存 R7 与金额、对象及状态，重试复用 R7；接收方支持幂等键时核对其有效期后再送。接收方若既不能去重也不能按 R7 查单，把结果标为待核，暂停第二次付款，交由对账处理。两笔独立的 80 元退款各自有不同意图 ID。

## A2 · 何时调用

适于评审重试扣费、跨服务约束、审计、个性化评分和用户纠错。流处理算子的状态恢复见流处理卡；仅讨论单库并发写入时转事务卡。

## E · 执行与验收

1. 画出意图产生、权威记录、派生视图和外部动作。在每条边标记确认时点、重试者、幂等键的作用域与保留期。
2. 在权威存储内原子地登记操作 ID 和对应业务效果或待投递记录。同 ID 同载荷返回已知状态，同 ID 不同载荷拒绝并核查。下游分别记录写入和真实外部履约的证据。
3. 指定独立对账源、差异阈值与补救责任。以退款为例，核对支付方结算明细、账本和用户可见余额，区分“尚未结算”和“重复支出”。若新旧派生视图迁移，先并行重建、比对同一位点，再切读。
4. 若输出影响个人，写出数据字段、用途、接收方、保留期限、纠错或清除如何传播到缓存与派生特征。给出可联系的责任角色、人工复核路径及误判后如何恢复权益。
5. 交付一张“业务约束／故障时可见结果／核查证据／处置负责人”表。用确认丢失、两个独立意图、源数据更正三个情景实测推演。

## B · 反例与判停

数据库事务提交不能证明第三方已付款。永久保留所有原始个人事件虽有利于重建，却会增加披露风险；应按目的评估最小字段、期限和恢复备份后重新应用删除的流程。合规期限和申诉时限需业务与相应责任人确认。
